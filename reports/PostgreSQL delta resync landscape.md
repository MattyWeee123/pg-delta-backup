# Chunk Hashing Fills PostgreSQL's Stale-Copy Gap

As of October 2026, no PostgreSQL tool, built-in or third-party, does what the CMU–AlloyDB project proposes: refresh an arbitrary older physical copy straight from a live server, verify every reused byte by content, and move data at finer than whole-file granularity. Core PostgreSQL's `pg_basebackup` still requires an empty target directory. The block-level incremental backup added in PostgreSQL 17, essentially unchanged in PG18 and the PG19 release candidate, works only against a previous backup that kept its manifest while the server kept change summaries covering the entire gap. `pg_rewind` only repairs a copy that forked onto a different history and still has its own logs. Third-party tools split the problem in two: pgBackRest verifies reused data by hash but restores only from its own backup repository, while pg_probackup and WAL-G can catch up a stale replica directly from the primary but trust page log positions (LSNs) and file timestamps, and require an unbroken shared history. Disk snapshots and cloud services (ZFS, EBS, Aurora, managed AlloyDB) send deltas cheaply only while both sides share an untouched ancestor, so the tool's natural home is self-managed PostgreSQL and AlloyDB Omni, where standbys, failover leftovers and restored snapshots are full physical copies with no usable lineage. Content hashing is the right correctness bet, because the obvious shortcut, comparing page LSNs, fails in at least nine documented situations, including a visibility-map bug that silently produced wrong PostgreSQL incremental backups until the August 2026 minor releases. Its price is reading every byte on both sides, so the tool wins decisively on bandwidth-limited or cross-region links and loses to a parallel full copy on very fast LANs. The evidence points to a specific design: page-aligned 8 KiB hashes rolled up into a hash tree (not content-defined chunking), a keyed 128-bit-or-stronger hash, hashing agents on both hosts, the standard backup start/stop protocol plus WAL replay for consistency, and LSNs or WAL summaries used to send pages sooner, never to skip them unchecked.

## PostgreSQL's own tools assume a known history, not an old copy

### The vocabulary behind every refresh decision

In PostgreSQL a *cluster* is not a group of machines but the set of databases one server manages, stored as ordinary files in a single *data directory* (conventionally called `PGDATA`). A *physical copy* duplicates those files byte for byte, unlike a *logical* copy rebuilt from SQL statements. Tables and indexes, collectively called *relations*, live in files made of fixed 8 KiB *pages* (also called blocks), split into 1 GiB *segment* files. Each relation also has side files called *forks*: the main data, a *free space map* (FSM) recording where new rows fit, a *visibility map* (VM) marking pages whose rows every transaction can see, and, for *unlogged* tables that skip crash protection, an *init fork* used to reset them to empty. Every change is first written to the *write-ahead log* (WAL), a sequential journal, and a position in that journal is a *log sequence number* (LSN), effectively a byte offset that only grows. Each page header stores `pd_lsn`, the position just past "the last byte of WAL record for last change to this page" ([PG page layout](https://www.postgresql.org/docs/18/storage-page-layout.html)), which is what makes "compare page LSNs" the tempting shortcut for spotting changes. A *checkpoint* flushes changed pages to disk, and its *redo point* is the LSN from which crash recovery must replay WAL. Because an 8 KiB write can be interrupted halfway, leaving a *torn page* that mixes old and new bytes, PostgreSQL logs a *full-page image* (FPI) of each page the first time it changes after a checkpoint, a setting called `full_page_writes` ([runtime-config-wal](https://www.postgresql.org/docs/18/runtime-config-wal.html)). *Hint bits* are small per-row flags that cache whether a transaction committed; they are set opportunistically, often during plain reads, and are protected by WAL only when *data checksums* (a 16-bit integrity code in each page) or the `wal_log_hints` setting are on ([runtime-config-wal](https://www.postgresql.org/docs/18/runtime-config-wal.html)). The small `pg_control` file holds the cluster's *system identifier* (a random ID fixed when the cluster is created), the latest checkpoint and the current *timeline*, a counter that increments whenever a copy is promoted to primary so that diverging histories get distinct names. A *standby* (or *replica*) is a copy that continuously replays WAL streamed from the *primary*. Finally, a copy read from a running server is never self-consistent: it becomes usable only after WAL replay from the copy's starting checkpoint, which a `backup_label` file instructs the server to perform ([continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html)).

### pg_basebackup copies everything, every time

The standard cloning tool streams every included file in full, one archive per *tablespace* (an extra storage location outside the data directory), and the target directory must be empty if it already exists ([pg_basebackup docs](https://www.postgresql.org/docs/18/app-pgbasebackup.html)). It skips a defined set of files, including server lock files, temporary relations, unlogged relations other than their init forks, replication-slot state and live WAL, and that exclusion list is the de facto contract for what belongs in a physical copy ([replication protocol docs](https://www.postgresql.org/docs/18/protocol-replication.html)). Its JSON *backup manifest* records **one checksum per file**, CRC32C by default (a fast 32-bit error-detecting code), plus a "Last-Modified" time the docs label informational ([backup manifest format](https://www.postgresql.org/docs/18/backup-manifest-files.html)). That is enough to tell that a file changed, never which page.

Delta transfer has been debated for fifteen years without landing in core. In 2011 Robert Haas suggested "differential copy, a la rsync," and Tom Lane answered that this reinvented the wheel and users should just run rsync ([Tom Lane, 2011](https://www.postgresql.org/message-id/9784.1302453336%40sss.pgh.pa.us)). In 2020 Stephen Frost listed delta restore among pg_basebackup's missing features, warned that rsync can't safely rebuild replicas unless run with checksums, "and even then it's complicated," and pointed to pgBackRest instead ([Stephen Frost, 2020](https://www.postgresql.org/message-id/20200521215306.GF3418%40tamriel.snowman.net)). The research found no 2024–2026 patch for destination-aware transfer or per-block manifest checksums, and the PG19 release candidate (RC1, 15 October 2026, not yet final) adds only a progress-view column and tar-WAL verification to the backup tools ([PG19 release notes](https://www.postgresql.org/docs/devel/release-19.html)). The gap hurts most in replication: when a standby falls so far behind that the primary has recycled WAL it still needs, the documented remedy is to reinitialize it "from a new base backup" ([high availability docs](https://www.postgresql.org/docs/18/warm-standby.html)), discarding the terabytes the standby already holds.

### PG17 incremental backup tracks changes at the source, against one known backup

PostgreSQL 17 (released 26 September 2024) added block-level incremental backup ([PG17 release notes](https://www.postgresql.org/docs/17/release-17.html)). A background *WAL summarizer* reads the log and records, for each relation fork, which block numbers changed between checkpoints, storing compact bitmaps in `pg_wal/summaries` ([walsummarizer.c](https://github.com/postgres/postgres/blob/master/src/backend/postmaster/walsummarizer.c)). Running `pg_basebackup --incremental=<previous backup_manifest>` uploads the old manifest; the server then sends, for each relation segment, an `INCREMENTAL.*` file holding only changed 8 KiB blocks, and sends every non-relation file whole ([continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html)). The prerequisites are strict. `summarize_wal` defaults to **off**, summaries older than `wal_summary_keep_time` (default **10 days**) are deleted ([runtime-config-wal](https://www.postgresql.org/docs/18/runtime-config-wal.html)), and summaries must cover every LSN between the two backups' start points or the backup fails ([continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html)). The server rejects old-format manifests and mismatched system identifiers, always sends the FSM whole because it "is not properly WAL-logged," and sends a segment whole once **more than 90%** of its blocks changed ([basebackup_incremental.c](https://github.com/postgres/postgres/blob/master/src/backend/backup/basebackup_incremental.c)). Turning the pieces back into a usable directory requires `pg_combinebackup` and every backup in the chain, which PostgreSQL itself does not track ([pg_combinebackup docs](https://www.postgresql.org/docs/18/app-pgcombinebackup.html); [continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html)). The output is always a new directory, though `--clone` (copy-on-write reflinks) and PG18's new `--link` avoid most physical copying ([PG18 release notes](https://www.postgresql.org/docs/18/release-18.html)).

Published measurements are thin and date from development. In Jakub Wartak's 24-hour pgbench test, a 3.4 GB full backup was followed by 11 incrementals totalling about 3.5 GB, **roughly one-tenth of a full backup each** ([pganalyze](https://pganalyze.com/blog/5mins-postgres-17-incremental-backups)). Tomas Vondra measured `pg_combinebackup` on a 75 GB database at **150–200 s** on ext4, XFS and Btrfs and **900–1,000 s on ZFS**; experimental batched `copy_file_range` patches cut the 1%-changed case on XFS to 4 s, but only with manifest checksums off, and he called them "not commit-ready" ([Vondra, 2024](https://www.postgresql.org/message-id/5ac425a4-6201-4f24-912e-8eed6905790a%40enterprisedb.com)). No TB-scale or production benchmarks were found. The design lesson is that incremental backup is the mirror image of the student project. It tracks changes at the source against a reference identified by its manifest's LSN range, so its read cost scales with changed blocks rather than database size, which is a real advantage. It is useless, however, when the destination has no manifest, predates `summarize_wal=on`, is older than the retention window, or has been modified since the manifest was written (a standby that kept replaying WAL, or a copy someone started).

### pg_rewind and rsync cover narrow cases

`pg_rewind` is core's only in-place, block-granular resynchronizer, and it targets one case: a former primary whose timeline forked from the new primary's after a failover. It scans the *target's own* WAL from the last checkpoint before the fork to list every block the target touched, copies those blocks plus every non-relation file and new relation file from the source, and leaves a `backup_label` so WAL replay finishes the job ([pg_rewind docs](https://www.postgresql.org/docs/18/app-pgrewind.html)). It requires `wal_log_hints=on` or data checksums (the latter on by default only for clusters initialized with PG18 or later, per the [PG18 release notes](https://www.postgresql.org/docs/18/release-18.html)), needs the target's WAL back to the fork (or a `restore_command` to fetch it), and the docs warn that a run failing midway likely leaves the target unrecoverable ([pg_rewind docs](https://www.postgresql.org/docs/18/app-pgrewind.html)). It cannot help a copy that is merely stale on the same timeline or whose WAL is gone.

For everything else the documentation offers rsync: copy while the server runs, then stop it and run `rsync --checksum`, which "is necessary because rsync only has file modification-time granularity of one second" ([file system backup docs](https://www.postgresql.org/docs/18/backup-file.html)). The pg_upgrade standby recipe uses `rsync --size-only --hard-links`, which is safe only because link-mode pg_upgrade guarantees that untouched files are byte-identical ([pg_upgrade docs](https://www.postgresql.org/docs/18/pgupgrade.html)). Stitching together the low-level backup API and the rsync advice yields the closest core-sanctioned way to reuse an old copy from a live server: call `pg_backup_start`, run `rsync --checksum`, call `pg_backup_stop`, write `backup_label`, replay WAL. That combination is not spelled out as one recipe in the docs, but it is the first baseline the project must beat.

## Third-party tools offer content verification or a live source, never both

Five commands in the ecosystem refresh an existing data directory in place, and they divide along two axes: where the truth comes from (a backup repository or the live primary) and how reuse is decided (by content hash, or by trusting LSNs and timestamps).

| Tool and command | Source of truth | How it decides destination data is reusable | Granularity | Key requirements |
|---|---|---|---|---|
| pgBackRest `restore --delta` | Its own repository | SHA-1 per file; xxHash per block for block-incremental files | File, or 8–88 KiB block | PostgreSQL stopped; `PG_VERSION` or manifest present in target |
| Barman `restore --delta-restore` (3.16+) | A Barman backup | rsync size/mtime check for old files, `rsync --checksum` for recent ones | rsync blocks | Plain backups only: not incremental, compressed or encrypted |
| pg_probackup `restore -I checksum` or `-I lsn` | Its own catalog | Page checksum plus LSN against the backup, or page LSN above a "shiftpoint" | 8 KiB page | Same system ID; LSN mode needs data checksums and a trustworthy `pg_control` |
| pg_probackup `catchup -b DELTA/PTRACK` | Live primary | Source page LSN at or above the destination's redo LSN | 8 KiB page | Same system ID; destination timeline within source history; destination stopped |
| WAL-G `catchup-send` / `catchup-receive` | Live primary | Equal file mtime skips a file; page LSN at or above destination checkpoint | 8 KiB page or file | Same system ID and the *same* timeline; destination stopped |

Sources for the table: [pgBackRest user guide](https://pgbackrest.org/user-guide.html), [Barman recovery docs](https://docs.pgbarman.org/release/3.20.1/user_guide/recovery.html), [pg_probackup docs](https://postgrespro.github.io/pg_probackup/), [WAL-G catchup source](https://github.com/wal-g/wal-g/blob/master/internal/databases/postgres/catchup_send_recieve_handler.go).

**pgBackRest** (v2.60.0, released 18 October 2026) is the closest analogue to a content-hash resync ([pgBackRest releases](https://github.com/pgbackrest/pgbackrest/releases)). Its delta restore computes "a SHA-1 cryptographic hash for each file" in the target, keeps matches and removes files absent from the backup ([user guide](https://pgbackrest.org/user-guide.html)). For *block-incremental* files (generally available since v2.46) it hashes the existing file per block with xxHash, fetches only blocks whose checksum differs from the repository's block map, then recomputes a whole-file SHA-1 as a safeguard ([restore/file.c.inc](https://github.com/pgbackrest/pgbackrest/blob/main/src/command/restore/file.c.inc); [blockDelta.c](https://github.com/pgbackrest/pgbackrest/blob/main/src/command/restore/blockDelta.c)). Two limits matter. Block size grows with file size and age, from 8 KiB up to **88 KiB for files near 1 GiB**, doubles or quadruples for files untouched for 7 or 14 days, and block incremental switches off entirely at 28 days ([option.c.inc](https://github.com/pgbackrest/pgbackrest/blob/main/src/command/backup/option.c.inc)), so one changed page in an old segment can cost hundreds of KiB. More fundamentally, the repository is the source of truth, so refreshing a stale copy from a live primary takes two hops (back up into the repository, then delta-restore) plus repository storage. On the backup side pgBackRest trusts file size and timestamp by default, switching to checksums only with `--delta` or when it detects anomalies such as a timeline switch or a timestamp moving backwards ([manifest.c](https://github.com/pgbackrest/pgbackrest/blob/main/src/info/manifest/manifest.c)). Its recent history shows how much of the ecosystem rests on one project: on 27 April 2026 the maintainer announced pgBackRest was "no longer being maintained," then reversed course on 18 May after a sponsor coalition including AWS, Supabase and Percona stepped in ([pgBackRest news](https://pgbackrest.org/news.html)).

**Barman** has two incompatible mechanisms: rsync-based file-level reuse (`reuse_backup`, since 2015) and PG17-native block incremental via `pg_basebackup --incremental` (since 3.11.0) ([Barman backup docs](https://docs.pgbarman.org/release/3.20.1/user_guide/backup.html)). Its in-place `--delta-restore` arrived in 3.16.0 (October 2025) and did not actually work until 3.17.0 (January 2026), because Barman was deleting the destination directory before restoring ([Barman release notes](https://docs.pgbarman.org/release/3.20.1/releases/index.html)). It supports only plain backups, so Barman cannot refresh a stale copy in place from a block-level chain ([recovery docs](https://docs.pgbarman.org/release/3.20.1/user_guide/recovery.html)). Barman decides what to re-check with a *safe horizon* timestamp: files older than the horizon get rsync's size-and-mtime quick check, newer ones get `--checksum` ([copy_controller.py](https://github.com/EnterpriseDB/barman/blob/master/src/barman/copy_controller.py)).

**WAL-G**'s delta backups pick files by modification time and pages by header LSN ([WAL-G docs](https://github.com/wal-g/wal-g/blob/master/docs/PostgreSQL.md)), and its normal restore refuses non-empty directories ([backup_fetch_handler.go](https://github.com/wal-g/wal-g/blob/master/internal/databases/postgres/backup_fetch_handler.go)). Its `catchup-send`/`catchup-receive` pair, however, refreshes a stopped standby straight over TCP. The receiver sends its `pg_control` and per-file mtimes; the sender aborts on a system-identifier or timeline mismatch, skips files whose mtime equals the destination's, sends pages with LSN at or above the destination's checkpoint, deletes files absent on the source, and ships `backup_label` and `pg_control` last ([catchup source](https://github.com/wal-g/wal-g/blob/master/internal/databases/postgres/catchup_send_recieve_handler.go)). The direct path exists because routing catchup through object storage "doubles the number of bytes that need to be transferred" ([WAL-G #1629](https://github.com/wal-g/wal-g/issues/1629)). It is not mature: catchup-send "doesn't work with tablespaces" ([#2068](https://github.com/wal-g/wal-g/issues/2068)), and a March 2026 pull request fixing four catchup bugs, including missing directory creation on the receiver, was still open when the research was done ([PR #2220](https://github.com/wal-g/wal-g/pull/2220)). A reading of WAL-G's source suggests it uses the location of the checkpoint record rather than the earlier redo point as its threshold ([pg_control_data.go](https://github.com/wal-g/wal-g/blob/master/internal/databases/postgres/pg_control_data.go)). Whether that can skip a page changed between the two positions is unverified, but it illustrates how subtle LSN thresholds are.

**pg_probackup** has the richest page-level toolkit. DELTA mode scans every page and compares its LSN with the parent backup, PAGE mode builds the changed-block map from archived WAL, and PTRACK uses an extension that records changes as they happen but needs Postgres Pro or a patched server ([pg_probackup docs](https://postgrespro.github.io/pg_probackup/)). Its `catchup` command is the closest existing match to the student tool: it can "update an existing replica much faster by bringing differences from master" without any backup catalog ([pg_probackup docs](https://postgrespro.github.io/pg_probackup/)). Its source checks system identifiers, refuses a running destination or a leftover `backup_label`, requires the destination's redo point to lie on the source's timeline history, and renames the destination's `pg_control` aside during the run ([catchup.c](https://github.com/postgrespro/pg_probackup/blob/master/src/catchup.c)). Its incremental restore offers a CHECKSUM mode the docs call "the most fool-proof," and an LSN mode that demands data checksums "to avoid corruption due to hint bits" ([pg_probackup docs](https://postgrespro.github.io/pg_probackup/)). The open-source project moves slowly: 2.5.16 (December 2025) added PG18 support, and a mode that uses PG17 WAL summaries remains an unmerged pull request ([releases](https://github.com/postgrespro/pg_probackup/releases); [PR #672](https://github.com/postgrespro/pg_probackup/pull/672)).

Orchestration layers add no change detection of their own. Patroni's `keep_data` flag is the one generic hook that lets `pgbackrest --delta restore` rebuild a replica in place ([Patroni docs](https://github.com/patroni/patroni/blob/master/docs/replica_bootstrap.rst)). Zalando's Spilo rebuilds replicas with a full WAL-G fetch or pg_basebackup ([configure_spilo.py](https://github.com/zalando/spilo/blob/master/postgres-appliance/scripts/configure_spilo.py)), CloudNativePG's object-store backups "do not support incremental or differential copies" and leave deltas to storage-level volume snapshots ([CNPG backup docs](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/docs/src/backup.md)), and repmgr falls back to pg_rewind ([repmgr node rejoin](https://www.repmgr.org/docs/current/repmgr-node-rejoin.html)).

No independent, controlled head-to-head benchmark of these delta mechanisms exists. The available figures are vendor demos. pgBackRest block incremental shrank an incremental backup of a roughly 1 GB database from 52.8 MB to 943 KB, and its delta restore copied 3.5 MB instead of 30.4 MB ([Crunchy Data](https://crunchydata.com/blog/pgbackrest-file-bundling-and-block-incremental-backup)). A pg_probackup LSN-mode restore moved 1,693 MB of a 15 GB data directory (11%) in 43 s ([pg_probackup commit](https://github.com/postgrespro/pg_probackup/commit/496605bdb50012788fbab74a0f1625df1a26a789)). The most useful full-copy reference comes from Postgres.ai: on a 1.02 TiB database over a 75 Gbps link, pg_basebackup took **950 s** while pgBackRest with 32 parallel processes took **101 s**, saturating the network ([Postgres.ai](https://postgres.ai/blog/20251105-postgres-marathon-2-012-ultra-fast-replica-creation-pgbackrest)). Read together, the matrix shows the gap: the content-verified tools need a repository, the live-source tools trust LSNs and mtimes, and none combines a live source, no repository, hash verification and sub-file granularity.

## Snapshots and clouds send deltas only while lineage is unbroken

### Filesystem and disk snapshots need an untouched shared ancestor

*Copy-on-write* (CoW) storage shares unchanged blocks between versions, so snapshots are cheap and the exact difference between two snapshots is known. ZFS's `zfs send -i` streams only blocks changed between two snapshots, but "the incremental source must be an earlier snapshot in the destination's history" ([zfs-send(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html)), and btrfs needs parent snapshots "available on both the sending and receiving side" ([btrfs-send(8)](https://btrfs.readthedocs.io/en/latest/btrfs-send.html)). The clouds work the same way. AWS's EBS direct APIs list "blocks that are different between two specified snapshots of the same volume and snapshot lineage," in **512 KiB** units ([EBS direct APIs](https://docs.aws.amazon.com/ebs/latest/userguide/ebsapi-elements.html)). Azure cannot diff snapshots taken before and after a disk resize across its 4 TB boundary, and SKU changes start a new snapshot family ([Azure incremental snapshots](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-incremental-snapshots)). A first EBS copy to a new region, or under a new encryption key, is always full ([EBS snapshot copy](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-copy-snapshot.html)). Granularity is coarse: by simple arithmetic, one scattered 8 KiB page change costs a 512 KiB EBS block, up to **64× amplification**, and at AWS's example price of $0.003 per 1,000 blocks read, pulling 1 TiB of changed blocks costs about $6 in API fees ([EBS direct API pricing](https://docs.aws.amazon.com/ebs/latest/userguide/ebsapi-pricing.html)).

PostgreSQL accepts any atomic snapshot as *crash-consistent*, meaning it starts as though the server had crashed and replays WAL, but only if the data directory, WAL and every tablespace are captured at the same instant ([file system backup docs](https://www.postgresql.org/docs/18/backup-file.html)). Once a restored copy is started, promoted or written to, the shared ancestor is gone unless it was preserved separately. That broken-lineage case is precisely the one a content-hash refresh addresses.

### Disaggregated services never reuse old copies, but AlloyDB Omni does

Managed "log-is-the-database" services ship only WAL from the compute node to a storage tier that builds pages itself, so copies become metadata operations. Aurora clones point "to the same set of pages as the source" using copy-on-write, up to 15 clones per source, and cannot cross regions ([Aurora cloning](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Clone.html)). Neon, part of Databricks since 2025, makes branches that are "copy-on-write views over shared storage" ([Neon and Lakebase](https://neon.com/docs/introduction/neon-and-lakebase)). Managed AlloyDB's storage layer runs a log processing service that turns WAL records into "materialized" blocks in regional block storage; read replicas need no storage of their own, and "backup operations are completely handled by the storage service" ([Google Cloud blog](https://cloud.google.com/blog/products/databases/alloydb-for-postgresql-intelligent-scalable-storage/)). Cross-region secondary clusters, up to five per primary, replicate asynchronously into a secondary storage volume, but Google's docs do not say how a secondary is first populated ([AlloyDB cross-region](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication)). Inside managed AlloyDB, a chunk-hash refresher has no job to do.

AlloyDB Omni, the self-managed edition, is different and is the project's natural customer. Google recommends pgBackRest for container deployments ([Omni backup overview](https://docs.cloud.google.com/alloydb/omni/containers/16.3.0/docs/backup-overview)). The Kubernetes operator schedules full, differential and incremental backups through a `backupPlan`, a `Restore` "overwrites all of your database cluster's data," and point-in-time clones work only "within the same namespace and same kubernetes cluster" ([Omni Kubernetes backup](https://docs.cloud.google.com/alloydb/omni/kubernetes/16.11.0/docs/backup-kubernetes)). High availability requires storage for two complete copies of the data, and failover promotes a standby, deletes the old primary and creates a new standby ([Omni Kubernetes HA](https://docs.cloud.google.com/alloydb/omni/kubernetes/18.1.0/docs/kubernetes-ha); this page was seen only as a search summary). Each of those events produces or throws away a full physical copy, which is exactly the raw material a delta refresher could reuse.

### Most old copies in the wild carry no pg_basebackup metadata

Managed services build their copies from volume snapshots plus WAL. RDS backups are storage volume snapshots and read replicas are created "from the snapshot" ([RDS backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html); [RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html)). Azure's Flexible Server uses managed-disk incremental snapshots ([Azure PG backup](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore)), and Cloud SQL backups are incremental over "the underlying storage snapshot" ([Cloud SQL backups](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups)). Recreating an RDS cross-region replica ships a full snapshot copy and "can take hours" ([RDS cross-Region replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.XRgn.html)), even if the destination region still holds a near-identical old copy. Customers can't touch those files, so the tool's market is self-managed clusters. There, the realistic old copies are restored disk or ZFS snapshots, former primaries and standbys after failover, restores from pgBackRest, WAL-G or Barman, and thin clones. None of these carries a PostgreSQL `backup_manifest` plus WAL summaries spanning the gap, so PG17 incremental cannot use them. No source measures how common each type is, so the premise that most real copies are not pg_basebackup outputs is plausible but unquantified.

## Other databases settled on three ways to find changed blocks

Every major database faces the same problem, and the answers fall into three families. The first scans every page and compares its header log position with the base, which needs no extra metadata but reads everything. The second keeps a server-maintained bitmap of changed blocks, which makes reads cheap but has bounded history and must catch every write path. The third compares content hashes, which needs no history but forces both sides to read everything.

| System | Refreshes a stale copy in place? | How changes are found | Notable limit |
|---|---|---|---|
| Oracle | Yes: `RECOVER STANDBY DATABASE FROM SERVICE` (18c+) | Blocks newer than the standby's datafile-header SCN; optional change-tracking bitmap | Bitmap keeps only 8 backups of history |
| MySQL (XtraBackup, Enterprise Backup) | No; incremental backups only | Page LSN scan, or a server page-tracking component | Enterprise Backup refuses page tracking at ≥50% pages changed |
| MySQL Clone plugin | No; wipes the recipient | File copy plus tracked dirty pages plus redo | New directory required to keep old data |
| Galera (MariaDB, Percona XtraDB Cluster) | Only via the `rsync_wan` transfer method | rsync rolling checksums | Default rsync method uses `--whole-file` |
| SQL Server | No; availability-group seeding streams a full backup | Differential bitmap, 1 bit per 64 KiB extent | 5 TB over 1 Gb/s takes about 11 hours |
| MongoDB | No; a stale member's data directory is wiped | Operation-log replay only within its window | Full initial sync otherwise |
| Cassandra, ScyllaDB | Yes, as logical repair | Merkle trees; per-row hashes with set reconciliation | Coarse trees overstream |
| SQLite `sqlite3_rsync` | Yes | Hierarchical page hashes sent from replica to origin | Both sides read the whole file |

Oracle is the only mainstream relational system that ships exactly the operation the project wants. Its *SCN* (system change number) plays the role of PostgreSQL's LSN. Since 12c, `RECOVER DATABASE FROM SERVICE ... NOREDO` builds an incremental backup on the primary containing changes "beginning with the SCN in the standby data file header," ships it over the network and applies it, skipping datafiles already current ([Redgate Simple Talk](https://www.red-gate.com/simple-talk/databases/oracle-databases/rolling-forward-a-physical-standby-database-using-the-recover-command/)). 18c collapsed this into one command, `RECOVER STANDBY DATABASE FROM SERVICE` ([Oracle 19c docs](https://docs.oracle.com/en/database/oracle/oracle-database/19/spmss/refresh-a-physical-standby-db.html)). Oracle's optional Block Change Tracking file is about **1/30,000 of database size**, covers only "the eight most recent backups," and is reset after a restore ([Oracle backup guide](https://docs.oracle.com/en/database/oracle/oracle-database/19/bradv/backing-up-database.html)).

MySQL shows how trackers fail. XtraBackup copies "each page which LSN is newer than the previous incremental or full backup's LSN" ([XtraBackup docs](https://docs.percona.com/percona-xtrabackup/8.0/create-incremental-backup.html)). Its newer page-tracking mode avoids the scan, but Oracle MySQL bug 106163 meant certain in-place DDL was never written to the redo log, producing inconsistent backups detected only at prepare time, and Percona documents that "you may generate a bad incremental backup using page tracking" ([page tracking docs](https://docs.percona.com/percona-xtrabackup/8.0/page-tracking.html)). MySQL Enterprise Backup errors out of page-track mode when at least half the pages changed, and its mtime-based "optimistic" mode warns of inconsistent backups if the system clock changes ([MEB docs](https://dev.mysql.com/doc/mysql-enterprise-backup/8.0/en/mysqlbackup.incremental.html)). The Clone plugin removes the recipient's data before copying ([MySQL Clone docs](https://dev.mysql.com/doc/refman/8.0/en/clone-plugin-remote.html)). Galera's `rsync_wan` method is the only MySQL-family path that reuses an old data directory, and it exists because rsync delta transfer "may reduce data transfer time substantially when an older datadir state is already present on the joiner node"; the default rsync method uses `--whole-file` instead ([MariaDB SST docs](https://mariadb.com/docs/galera-cluster/high-availability/state-snapshot-transfers-ssts-in-galera-cluster/introduction-to-state-snapshot-transfers-ssts/)).

SQL Server and MongoDB show the cost of having no refresh path at all. SQL Server's differential backups read a bitmap with one bit per 64 KiB extent, so their time is "proportional to the number of extents modified ... and not the total size of the database" ([page and extent guide](https://learn.microsoft.com/en-us/sql/relational-databases/pages-and-extents-architecture-guide)), but a lagging availability-group secondary is reseeded by streaming a full backup; Microsoft's own example is 5 TB over 1 Gb/s taking "just over 11 hours," during which the primary's log cannot be truncated ([automatic seeding](https://learn.microsoft.com/en-us/sql/database-engine/availability-groups/windows/automatic-seeding-secondary-replicas)). A stale MongoDB member must be completely resynchronized by removing its data, and initial sync deletes the contents of its data directory ([MongoDB resync docs](https://www.mongodb.com/docs/manual/tutorial/resync-replica-set-member/)).

The content-hashing family is where the closest design precedents live. Cassandra repair compares replicas with *Merkle trees*, hash trees in which each node hashes its children so that equal roots prove whole subtrees equal ([Cassandra repair docs](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/repair.html)). ScyllaDB 3.1 moved from checksums over about 100 partitions to per-row hashes with *set reconciliation* (exchanging only the elements two sets disagree on); for replicas 99.9% in sync, repair time fell from 96.4 to 14.2 minutes and data sent from **120.52 GiB to 4.28 GiB** ([ScyllaDB blog](https://www.scylladb.com/2019/08/13/scylla-open-source-3-1-efficiently-maintaining-consistency-with-row-level-repair/)). SQLite's `sqlite3_rsync` (3.47.0, October 2024) is the nearest single-node analogue: the replica sends cryptographic hashes of pages or groups of pages, the origin returns differing pages and asks for finer hashes where a group mismatches, and traffic is "often less than 0.01%" of database size, about 20 KB for a 500 MB database ([sqlite3_rsync docs](https://sqlite.org/rsync.html)). Before version 3.50.0, per-page hashing gave a floor of roughly 0.5% of database size even for identical files, which group-level hashing removed ([sqlite3_rsync docs](https://sqlite.org/rsync.html)).

The pattern is instructive. Content hashing appears where copies lack a trustworthy shared log position (Cassandra replicas compact independently; SQLite has no global LSN) or where the tool must tolerate arbitrary divergence. PostgreSQL copies usually do share block numbering and LSNs, which is why PG tools favour the LSN and tracker families, but the scenarios in the previous section are precisely those where the sharing has broken. MySQL's in-place DDL bug foreshadows PostgreSQL's own VM bug below: trackers fail silently whenever a write path escapes logging.

## Delta-sync research says align to pages and stop scanning everything

### rsync's best trick is wasted on data that never moves

rsync's receiver sends, for each fixed-size block of its old file, a weak 32-bit *rolling checksum* (one that can slide forward one byte at a time cheaply) plus a stronger hash; the sender slides over its new file byte by byte to find matching blocks at any offset and sends literal bytes for the rest ([rsync tech report](https://rsync.samba.org/tech_report/)). Modern rsync sets block size to roughly the square root of file length, with a 700-byte floor and a 128 KiB cap ([generator.c](https://raw.githubusercontent.com/RsyncProject/rsync/master/generator.c); [rsync.h](https://raw.githubusercontent.com/RsyncProject/rsync/master/rsync.h)). For a 1 GiB PostgreSQL segment that means 32 KiB blocks, so by simple arithmetic one dirty 8 KiB page resends 32 KiB, and if 1% of pages are randomly dirty about 4% of blocks are resent (at 10%, about 34%). Copies between local paths default to `--whole-file`, which disables the delta algorithm entirely, and without `--inplace` rsync rewrites the whole destination file even for one changed block ([rsync(1)](https://download.samba.org/pub/rsync/rsync.1)). Current rsync also caps hash-chain lengths because disk images with long runs of identical blocks caused "multi-hour 'hangs'" ([match.c](https://raw.githubusercontent.com/RsyncProject/rsync/master/match.c)), a real risk for PostgreSQL files full of all-zero pages. Since PostgreSQL pages never move within a file, rsync's byte-offset search is pure overhead here. The zsync variant is more relevant: it publishes precomputed per-block checksums once so clients compare locally ([zsync paper](http://zsync.moria.org.uk/paper/)), which maps directly onto keeping a per-page hash manifest from the previous run.

### Content-defined chunking solves a problem PostgreSQL files do not have

*Content-defined chunking* (CDC) places chunk boundaries wherever a rolling hash of the content matches a pattern, so inserting bytes moves only nearby boundaries. LBFS (2001) introduced it with 8 KB expected chunks precisely because inserting data would "change the hashes of all the file's blocks" under fixed alignment, and found that smaller chunks found more shared data but the extra protocol traffic outweighed the gain ([LBFS paper](https://pdos.csail.mit.edu/papers/lbfs:sosp01/lbfs.pdf)). Chunking speed is no longer a barrier: FastCDC is about 10× faster than Rabin-based CDC ([FastCDC](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia)), and SeqCDC reaches 5.3–5.4 GB/s at 8 KB chunks and 30.5 GB/s with AVX-512 at 16 KB ([SeqCDC](https://arxiv.org/html/2505.21194v1)). Backup tools pick large average chunks to keep their indexes small: 64 KiB in casync, about 1 MiB in restic and about 2 MiB in borg ([casync](https://0pointer.net/blog/casync-a-tool-for-distributing-file-system-images.html); [restic](https://restic.readthedocs.io/en/latest/100_references.html); [borg](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)). With 1 MiB chunks, one dirty page re-uploads about 1 MiB, and 1% randomly dirty pages change roughly 72% of chunks.

PostgreSQL relation files only ever see in-place page substitutions, so CDC's one advantage never applies, while its boundaries fall mid-page (a dirty page typically overlaps two chunks), its scan burns CPU, and its variable sizes need explicit offset metadata. Even borg offers a fixed-size chunker and recommends block sizes that are multiples of the page size ([borg](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)). One result cuts the other way and a reviewer may cite it: in the vectorized SeqCDC paper, fixed 8 KB chunking on a "TPCC" dataset saved only 37.39% versus about 86–87% for CDC ([SeqCDC](https://arxiv.org/html/2505.21194v1)). Whether that dataset was raw, page-aligned database files or shifted data such as dumps was not verified, so the project should check before relying on either reading. CDC would only matter for reusing data across files after table rewrites (`VACUUM FULL`, `CLUSTER`), and even then differing page headers and LSNs defeat whole-page matches.

### Hashing is fast enough, so hash strength is the real choice

| Hash | Reported single-core throughput | Collision safety | Fit for skip decisions |
|---|---|---|---|
| XXH3 / XXH128 (AVX2) | 59.4 / 57.9 GB/s on an i7-9700K ([xxHash](https://github.com/Cyan4973/xxHash)) | Statistically strong at 128 bits; no protection against crafted inputs | Only for trusted data |
| CRC32C (hardware) | Roughly 20+ GB/s with 3-way interleaving ([Go issue 16107](https://golang.org/issue/16107)) | 32 bits is far too short | No |
| BLAKE3 | 12× SHA-256 single-threaded; steady beyond 16 KiB inputs ([BLAKE3 paper](https://github.com/BLAKE3-team/BLAKE3-specs/blob/master/blake3.pdf)) | Cryptographic; has a keyed mode | Yes |
| SHA-256 with SHA-NI | About 1.57 GB/s at 8–16 KB buffers ([BoringSSL](https://boringssl.googlesource.com/boringssl/+/17c8c811049a82d6c34897c718503444529c8d8b)) | Cryptographic | Yes, but needs 2–4 cores per NVMe drive |
| SHA-1 / MD5 (software) | 0.8 / 0.6 GB/s ([xxHash](https://github.com/Cyan4973/xxHash)) | Broken against adversaries | No |

Since fast NVMe drives read at roughly 2–7 GB/s, XXH3 and BLAKE3 keep up on one core while SHA-256 needs several. BLAKE3 is less efficient on single 8 KiB pages than on larger inputs, which favours hashing 64 KiB–1 MiB regions directly and computing per-page hashes only inside regions that differ. Collision risk splits sharply by use. For *positional* comparison (old page *i* against new page *i*), a 10 TiB cluster has about 1.34 billion pages, so the chance of any false "unchanged" is about 7×10⁻¹¹ with 64-bit hashes and about 4×10⁻³⁰ with 128-bit hashes (birthday-bound arithmetic). Content-addressed deduplication across all those pages would have about a 5% collision chance at 64 bits. The bigger issue is adversarial: table contents are user-controlled, and non-cryptographic hashes give no guarantee against deliberately crafted collisions, so a hostile user could in principle make a changed page look unchanged. A keyed cryptographic hash with a secret per-run key removes that risk. Real systems show the stakes: pg_probackup once reused a stale `pg_filenode.map` (the file mapping system catalogs to their data files) because of a "false-positive crc match," which "could break pg_catalog relations" ([pg_probackup releases](https://github.com/postgrespro/pg_probackup/releases)).

### The research frontier is to reconcile less and scan less

Academic delta-sync work since about 2015 accepts rsync's bandwidth efficiency and attacks compute cost. PandaSync chooses adaptively between full and delta sync and reports 85.1% lower average sync time than always using delta sync ([PandaSync](https://ranger.uta.edu/~jiang/publication/Conferences/2019/2019-ICDCS-PandaSync.pdf)). The biggest wins come from not scanning at all. dsync (LISA 2013) tracked block writes inside the Linux kernel and cut sync time "by up to two orders of magnitude" against checksum-based methods on hundreds of gigabytes ([dsync](https://usenix.org/conference/lisa13/technical-sessions/papers/knauth)). SkySync (FAST 2026) reuses checksums the storage layer already keeps and reports up to 89.3% less computation and 1.1–2× faster sync, noting that even CDC schemes "still need to calculate weak checksums of all bytes in the file" ([SkySync](https://www.usenix.org/conference/fast26/presentation/zhang-zhihao)). For PostgreSQL, dsync's analogue is the WAL summary and SkySync's is a stored per-page hash manifest from the previous refresh.

Theory says how little must cross the wire. For *t* edits in a file of length *n*, the lower bound is about *t*·log *n* bits, reachable within a constant factor in about log *t* interactive rounds ([Venkataramanan et al.](https://arxiv.org/abs/1310.2026)), or in one round with invertible Bloom filter "difference digests" whose size scales with the difference rather than the data ([Eppstein et al.](https://research.google/pubs/whats-the-difference-efficient-set-reconciliation-without-prior-context/)). PostgreSQL's case is simpler than general file sync because nothing shifts: it reduces to comparing a fixed vector of page hashes. A flat list costs about 2 MiB per 1 GiB segment at 16 bytes per page, while a Merkle tree with 1 MiB (128-page) nodes costs about 16 KiB per segment at its first level and descends only where nodes differ, typically in two or three round trips. Dynamo popularized exactly this anti-entropy shape ([Dynamo paper](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)).

### One percent of rows can dirty most of the pages

Row-level change and page-level change are very different quantities. Tomas Vondra measured that one hour of 5,000 inserts per second produced about 2 GB of WAL with sequential BIGSERIAL keys but over 40 GB with random UUID keys, because random keys touch random index pages, each triggering a full-page image ([EDB blog](https://www.enterprisedb.com/blog/impact-full-page-writes)). A simple probability model makes the same point for a stale copy: with 100 rows per page, randomly updating 1% of rows dirties about 63% of heap pages (1 − e⁻¹), 0.1% of rows dirties about 9.5%, and 5% dirties nearly all of them. A days-old copy of a hot, randomly updated table therefore approaches a full transfer, while append-mostly or time-partitioned tables stay cheap. No published study measures real dirty-page fractions for PostgreSQL workloads, so the project's benefit depends on a quantity nobody has measured. The CMU paper dbDedup offers one further lever: encoding records as byte-level deltas against similar records cut storage and replication traffic up to **37×** (61× with compression) ([dbDedup, SIGMOD 2017](https://pdl.cmu.edu/PDL-FTP/Database/xu-sigmod17_abs.shtml)), which suggests sending changed pages as compressed binary diffs against the destination's old page, an idea untested for PostgreSQL.

## Page LSNs mislead in at least nine documented situations

The tempting shortcut, "send only pages whose LSN is newer than the old copy," is correct only for main-fork pages of permanent relations, with hint bits WAL-logged, the right threshold, and one unbroken history. Every serious tool, including pg_rewind, PG17 incremental backup and WAL-G, copies the exceptions wholesale.

| Situation | What breaks the LSN or tracker shortcut | Evidence | Safe handling |
|---|---|---|---|
| Hint bits with checksums and `wal_log_hints` off | Page bytes change while `pd_lsn` stays old | [runtime-config-wal](https://www.postgresql.org/docs/18/runtime-config-wal.html); [bufmgr.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/bufmgr.c) | Hash; allow LSN logic only if checksums stayed on throughout |
| Free space map fork | Not fully WAL-logged; standby FSMs drifted until 17.10/18.4 | [walsummarizer.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/postmaster/walsummarizer.c); [17.10 notes](https://www.postgresql.org/docs/release/17.10/) | Always hash or copy whole |
| Visibility map bit clears | No LSN bump or block registration before 17.11/18.6 | [commit f581fa7](https://github.com/postgres/postgres/commit/f581fa729d8e108fef853c3156267b1f753d0210) | Always hash or copy whole |
| Unlogged and temporary relations | Never WAL-logged at all | [basebackup.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/backup/basebackup.c); [init fork docs](https://www.postgresql.org/docs/18/storage-init.html) | Exclude, but keep init forks |

Three of these deserve emphasis. First, the visibility-map bug is the cautionary tale for any change tracker. A commit by Melanie Plageman and Andres Freund in July 2026 explains that heap WAL records clearing VM bits "did not register the visibility map blocks they modified," so incremental backups "would omit the changed VM pages" and restored copies could give "wrong results from index-only scans"; the fix "does not repair existing incremental backups" ([commit f581fa7](https://github.com/postgres/postgres/commit/f581fa729d8e108fef853c3156267b1f753d0210)). It shipped in **17.11 and 18.6 on 13 August 2026** ([17.11 notes](https://www.postgresql.org/docs/release/17.11/)), nearly two years after PG17's release, even though the underlying hazard was raised on pgsql-hackers in 2017 by WAL-G's Andrey Borodin, who disabled increments for the FSM, VM and transaction-status files as a result ([2017 thread](https://www.postgresql.org/message-id/flat/F0627DEB-7D0D-429B-97A9-D321450365B4%40yandex-team.ru)). Second, PostgreSQL's own WAL summarizer calls the FILE_COPY case potentially "catastrophic," because a tablespace dropped and recreated by directory copy "would look just like one that was never touched at all," so it marks the whole database directory as recreated ([walsummarizer.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/postmaster/walsummarizer.c)). Third, the server's own code admits its identity checks are incomplete: two standbys promoted onto the same new timeline number can generate WAL "on the same timeline with the same LSNs more than once" without tripping any check ([basebackup_incremental.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/backup/basebackup_incremental.c)).

### The threshold must be the old copy's redo point

Even with checksums on, a hint-bit change logs a full-page image only if it is the page's first change since the last checkpoint, and sets the page LSN only when it wrote that image ([bufmgr.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/storage/buffer/bufmgr.c)). A page can therefore change after LSN *X* while still showing an LSN older than *X*. The only safe threshold is the redo point of the checkpoint the old copy's recovery began from, which is the "REDO location" in `pg_control` for a cleanly stopped copy, and every page at or above it must be sent. pg_probackup uses the destination's redo LSN, and PostgreSQL's own base backup treats any page with LSN at or above the backup start as possibly mid-write ([basebackup.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/backup/basebackup.c); [pg_probackup docs](https://postgrespro.github.io/pg_probackup/)).

### A live source is safe only with backup mode and WAL replay

Reading a running server's files captures torn and mutually inconsistent pages. The docs say `full_page_writes` "is effectively forced on during backup mode" and "any internal inconsistency in the backup will be corrected by log replay," provided all WAL from the backup's start to its end is kept ([continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html)). That is what makes hashing a live source safe: if a page changes after the backup's start LSN, its hash may reflect a torn image, but replay will overwrite it with a full-page image. One consequence follows by reasoning rather than from a source: source pages must be read only after `pg_backup_start` returns, because a page changed between an earlier read and the start checkpoint would never be replayed. Missing WAL is dangerous too; until 17.8, recovery "might crash or corrupt the database" if WAL did not reach back to the checkpoint's redo point ([17.8 notes](https://www.postgresql.org/docs/release/17.8/)).

### Timestamps, sizes and weak hashes have each caused silent staleness

Tom Lane's objections to file modification times are the canonical list: unknown timestamp granularity, clocks that can be set backwards, and filesystems that skip or delay updates ([2017 thread](https://www.postgresql.org/message-id/flat/F0627DEB-7D0D-429B-97A9-D321450365B4%40yandex-team.ru)). WAL-G mitigates this by skipping a file only when its mtime is exactly equal to the recorded one ([bundle.go](https://github.com/wal-g/wal-g/blob/master/internal/databases/postgres/bundle.go)). pgBackRest v2.28 fixed a bug in which `restore --force` compared timestamp and size, so "some files that should have been updated were left unchanged" ([pgBackRest release notes](https://pgbackrest.org/release.html)). The bug history across the ecosystem reads like a test plan.

| PG 17.10 / 18.4 (May 2026) | pg_basebackup, pg_rewind | CVE-2026-6475: a malicious source "could overwrite any file writable by these applications" ([17.10 notes](https://www.postgresql.org/docs/release/17.10/)) | Validate every path received from the source |

### Verification proves integrity, not freshness

PostgreSQL's verification tools catch different damage, and none proves a delta copy has the right *version* of every page. `pg_verifybackup` checks file presence, sizes, checksums and WAL parseability but "does not and cannot include every check which will be performed by a running server" ([pg_verifybackup docs](https://www.postgresql.org/docs/18/app-pgverifybackup.html)). A stale page from yesterday carries a perfectly valid page checksum, which is exactly why the VM bug went unnoticed. In WAL-G issue #1723, `bt_index_check` passed on the source while the restored copy was broken ([#1723](https://github.com/wal-g/wal-g/issues/1723)). On identity, `pg_rewind` aborts when "source and target clusters are from different systems" ([pg_rewind.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/bin/pg_rewind/pg_rewind.c)), but because pg_upgrade restarts WAL on timeline 1 ([pg_upgrade.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/bin/pg_upgrade/pg_upgrade.c)), the system identifier, not the timeline, is what distinguishes a post-upgrade cluster from its pre-upgrade copy.

## What this means for the CMU–AlloyDB tool

### Claim the lineage-free niche, and say plainly what the tool is not

The defensible one-sentence position is: the only PostgreSQL tool that refreshes any older physical copy of a cluster directly from a live server, verifying every reused page with a strong hash, with no backup repository, manifest, WAL summaries or shared timeline required. The concrete use cases, in order of how clearly the evidence supports them, are re-seeding a standby whose WAL was recycled (core's only answer is a full base backup), rebuilding an ex-primary when pg_rewind can't run (missing WAL, or hint bits unlogged on a pre-PG18 cluster), refreshing a disaster-recovery copy in another region or Kubernetes cluster from a restored snapshot (Omni's own clones stay within one namespace), and refreshing development copies from production. The tool should not claim to be a backup system (it offers no retention or point-in-time recovery), to help inside managed AlloyDB, to read less than PG17 incremental when that feature's prerequisites hold, or to beat a parallel full copy on a very fast LAN.

That last limit deserves numbers in every presentation. A 1 TiB full copy over a 1 Gb/s link takes about 2.4 hours; reading 1 TiB at 3 GB/s takes about 6 minutes per side in parallel, and if 2% of pages differ, roughly 20 GiB crosses the wire in about 3 minutes, so the tool wins by roughly 15–25× depending on how well reading and sending overlap. Over 75 Gbps, pgBackRest copies the same terabyte in 101 s ([Postgres.ai](https://postgres.ai/blog/20251105-postgres-marathon-2-012-ultra-fast-replica-creation-pgbackrest)), faster than the tool can read both sides at the 3 GB/s assumed above. The crossover is where network bytes are scarcer than disk reads: WAN links, cross-region egress and shared networks. Galera's default `--whole-file` choice reflects the same trade-off ([MariaDB SST docs](https://mariadb.com/docs/galera-cluster/high-availability/state-snapshot-transfers-ssts-in-galera-cluster/introduction-to-state-snapshot-transfers-ssts/)).

### Twelve design decisions the evidence already settles

| Decision | Recommendation | Why |
|---|---|---|
| Consistency | Bracket the run with `pg_backup_start`/`pg_backup_stop`; stream WAL from start to stop LSN over a replication connection with a temporary slot, as `pg_basebackup -X stream` does; write `backup_label` and `tablespace_map` byte for byte; finish with WAL replay | Live reads are torn; backup mode forces full-page writes so replay repairs them ([continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html); [pg_basebackup docs](https://www.postgresql.org/docs/18/app-pgbasebackup.html)) |
| Read ordering | Read and hash source pages only after `pg_backup_start` returns; destination hashes can be precomputed while it is stopped | Changes made before the start checkpoint are never replayed (reasoned from the replay model) |
| Where hashing runs | A small agent beside the source data directory and one beside the destination; only hashes and differing pages cross the network | The `BASE_BACKUP` protocol streams whole files, so a client-only design receives every byte; pg_rewind's SQL-only mode needs superuser rights or EXECUTE grants on `pg_read_binary_file` and related functions ([pg_rewind docs](https://www.postgresql.org/docs/18/app-pgrewind.html)) |
| Chunk unit | Fixed, page-aligned 8 KiB leaves; no content-defined chunking | Pages never shift; CDC exists only to handle insertions ([LBFS](https://pdos.csail.mit.edu/papers/lbfs:sosp01/lbfs.pdf)) |
| Hash tree | Segment root, then 1 MiB (128-page) nodes, then page leaves only under mismatched nodes | Cuts metadata from about 2 MiB to about 16 KiB per segment in the common case, as `sqlite3_rsync`'s multi-level hashing does ([sqlite3_rsync](https://sqlite.org/rsync.html)) |
| Hash function | Keyed BLAKE3 with a random per-run key by default; XXH3-128 only as an opt-in mode for trusted data; never CRC32C or the 16-bit page checksum | Throughput table above; pg_probackup's CRC false positive; user-controlled page contents |
| Metadata shortcuts | Use page LSN at or above the destination's redo LSN, or WAL summaries, to add pages to the send set early; skip unchecked only in an experimental mode gated on every identity check | Sending an extra page is always correct; skipping a changed one is silent corruption (nine pitfalls above) |
| High-churn fallback | When a node's mismatch rate passes a measured threshold (start near 50%), stop descending and stream the segment compressed | MySQL Enterprise Backup refuses page tracking at ≥50% ([MEB docs](https://dev.mysql.com/doc/mysql-enterprise-backup/8.0/en/mysqlbackup.incremental.html)); PG sends whole above 90%; PandaSync |
| File set | Mirror `BASE_BACKUP`'s exclusion list; delete destination files absent on the source; truncate oversize files before comparing; hash non-relation files whole | [Protocol docs](https://www.postgresql.org/docs/18/protocol-replication.html); truncation bugs above |
| Destination safety | Refuse if `postmaster.pid` exists; open the source read-only; move `pg_control` aside first and write it and `backup_label` last; fsync; reject paths with `..` or absolute components from the source | pg_probackup's rename trick ([catchup.c](https://github.com/postgrespro/pg_probackup/blob/master/src/catchup.c)); CVE-2026-6475 |
| Identity gate | Compare system identifier, major and catalog version, block and segment size, and checksum version; check the destination's redo timeline lies in the source's history; record both minor versions | pg_rewind and pg_probackup checks; pg_upgrade's timeline reset; VM-bug window before 17.11/18.6 |
| Output and verification | Emit a standard PostgreSQL `backup_manifest` so `pg_verifybackup` can audit the copy; re-hash the destination, recover to the stop LSN, run `pg_amcheck --heapallindexed`, and schedule periodic full-hash passes | Verification tools catch corruption, not staleness ([pg_verifybackup docs](https://www.postgresql.org/docs/18/app-pgverifybackup.html); [amcheck](https://www.postgresql.org/docs/18/amcheck.html)) |

One refinement follows from SkySync's result: cache the destination's hash tree after each refresh and reuse it next time if the destination's `pg_control` is unchanged, meaning it was never started, which avoids re-reading the old copy. Once the destination has run, the cache is worthless, because standby replay and hint bits rewrite pages.

### Benchmark against the baselines a reviewer will ask for

The research found no apples-to-apples benchmark of any PostgreSQL resync mechanism, so a careful comparison is itself a contribution. The baselines are full `pg_basebackup`; PG17/18 `--incremental` plus `pg_combinebackup` in copy and clone/link modes, with and without manifest checksums; `pg_probackup catchup -b DELTA`; WAL-G `catchup-send`; pgBackRest backup followed by delta restore (two hops); `rsync --checksum --no-whole-file --inplace --block-size=8192` inside `pg_backup_start`/`pg_backup_stop`; and pg_rewind where it applies. Stale-copy scenarios should include a lagging standby on the same timeline whose WAL was recycled, an ex-primary after failover, a restored disk snapshot, and a cluster after `pg_upgrade --link`. Workloads should vary the fraction of rows changed (0.1%, 1%, 10%, 50%) under uniform random updates versus append-only inserts, because the dirty-page arithmetic above predicts very different outcomes. Networks should span roughly 75 Gbps, 10 Gbps, 1 Gbps and a throttled 100 Mbps WAN. Metrics should cover bytes on the wire, bytes read on each side, bytes written at the destination, wall time, CPU per side per hash function, and post-refresh recovery time, reported as break-even curves against bandwidth. For ground truth, PG17's `pg_wal_summary_contents()` ([PG17 release notes](https://www.postgresql.org/docs/17/release-17.html)) lists changed blocks independently of the tool. Pages the tool sends that summaries omit should all be explained by hint bits, FSM or VM, and anything else is a bug in one of the two.

### Turn every documented failure into a regression test

Each row of the pitfalls table converts into a scripted test: hint-bit-only changes on a cluster initialized with `--no-data-checksums`; VACUUM truncating a table over 1 GB; dropping and recreating a database with `STRATEGY FILE_COPY`; `ALTER DATABASE SET TABLESPACE`; `pg_checksums --enable` between refreshes; an ex-primary that wrote WAL after failover; `pg_upgrade --link`; unlogged tables and temporary files present at refresh time. Fault-injection tests should kill the tool midway and confirm the destination refuses to start, then confirm a rerun completes; use identical source and destination path strings on two hosts; feed path-traversal file names; and, in the weak-hash mode, plant a crafted colliding page to demonstrate why the keyed hash is the default. The pass criteria are that a post-refresh re-hash matches the source's hash tree, recovery reaches consistency, `pg_amcheck --heapallindexed` is clean, and row counts or query checksums match the source at the same LSN.

### Questions to settle with the AlloyDB team

The research did not cover AlloyDB Omni's on-disk layout, so the first question is whether Omni's data directory contains files or page formats beyond vanilla PostgreSQL that the exclusion list and identity gate must handle. Second, it is unknown whether the Omni operator's `backupPlan` uses pgBackRest internally, how it seeds a new standby, and whether it could retain a failed primary's volume for the tool to refresh instead of deleting it; that last capability is the most compelling demo. Third, how Omni's transparent data encryption treats page headers matters. pgBackRest notes that with the pg_tde extension "every encrypted file fails the page checksum" ([pgBackRest release notes](https://pgbackrest.org/release.html)), which suggests LSN-reading tools struggle on encrypted pages while raw-byte hashing should work, provided identical plaintext encrypts identically within one cluster, which needs confirming. Fourth, Google's docs do not say how managed AlloyDB first seeds a cross-region secondary, a possible internal use case worth asking about. Finally, the team's target network profile decides whether the tool wins at all.

## Conclusion

The gap the project targets is not an oversight but a consequence of design: every existing mechanism is built on *lineage*, whether an LSN range, a backup repository, a snapshot chain or a shared timeline, and works only while that lineage holds. Content hashing is the one primitive that needs none, and its real selling point is the asymmetry of its failures. When a tracker or LSN shortcut is wrong, the result is a stale page that passes every checksum, as PostgreSQL's own VM bug showed across nearly two years of releases. When a strong keyed hash comparison errs on the cautious side, the cost is an unnecessary page sent. For a tool whose output becomes someone's production standby, that trade favours hashing.

The strongest version of the project is therefore a hybrid, matching where systems research has already gone: hashes decide what is true, while WAL summaries, page LSNs and cached hash trees decide what to read and send first. The project can also contribute something beyond code. Nobody has published a controlled comparison of PostgreSQL resync mechanisms, nor real dirty-page fractions for PostgreSQL workloads, and both numbers would determine where chunk-hash refresh beats incremental backup, catchup tools and a fast full copy. Producing them would make the tool's positioning evidence-based rather than argued.
