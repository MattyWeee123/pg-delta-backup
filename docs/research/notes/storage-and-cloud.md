# Storage-level and cloud-managed approaches to copying and refreshing PostgreSQL clusters (as of October 2026)

Scope: how filesystems, block storage, and cloud database services create or refresh database copies without re-sending everything; what consistency they give PostgreSQL; and what that says about where "older copies" of a Postgres cluster come from in practice. Research date: 2026-10-22. Pages were fetched on that date unless marked "(search-result summary; page not fetched)". Those secondary items should be checked before anyone quotes them.

---

## 1. Filesystem and volume snapshots (ZFS, btrfs, LVM thin) for PostgreSQL: incremental transfer and consistency

### Takeaway
ZFS (`zfs send -i/-I`, resumable sends, bookmarks) and btrfs (`send -p/-c`) can send only the blocks that changed between two snapshots, and LVM thin snapshots give cheap copy-on-write copies. Incremental transfer only works when both sides hold the same ancestor snapshot. PostgreSQL treats any atomic volume snapshot as crash-consistent. It is safe only if the data directory, WAL, and every tablespace are captured at the same instant. Otherwise the snapshot has to be wrapped in `pg_backup_start`/`pg_backup_stop` and restored with archive recovery.

### Cited Findings
**PostgreSQL's own rules for snapshots** (the `/docs/current/` page rendered as the PostgreSQL 18 docs when fetched)
- A "frozen snapshot" of the volume holding the data directory is an accepted way to back up a running server. The result looks to PostgreSQL like a server that "was not properly shut down", so when it starts it "will think the previous server instance crashed and will replay the WAL log". The docs say to "be sure to include the WAL files in your backup", and suggest a `CHECKPOINT` beforehand to shorten recovery. — [PostgreSQL docs: File System Level Backup](https://www.postgresql.org/docs/current/backup-file.html)
- Multi-volume caveat: "if your data files and WAL log are on different disks, or if tablespaces are on different file systems, it might not be possible to use snapshot backup because the snapshots *must* be simultaneous." The two alternatives are to shut the server down while the snapshots are taken, or to take a continuous-archiving base backup, which is "immune to file system changes during the backup." — [PostgreSQL docs: File System Level Backup](https://www.postgresql.org/docs/current/backup-file.html)
- File-level copies only work for the whole cluster, not single databases or tables, because `pg_xact/*` is required. — [PostgreSQL docs: File System Level Backup](https://www.postgresql.org/docs/current/backup-file.html)
- The docs also describe an rsync-based refresh: run rsync while the server is up, then stop the server and run `rsync --checksum`. `--checksum` is needed because rsync's mtime granularity is one second. "The second rsync will be quicker than the first." — [PostgreSQL docs: File System Level Backup](https://www.postgresql.org/docs/current/backup-file.html)
- Low-level API, which any file-copy or snapshot tool can be wrapped in: the connection that called `pg_backup_start` must stay open until `pg_backup_stop`, or the backup is aborted. `pg_backup_stop` returns the contents of `backup_label` and `tablespace_map`, which "must be written byte for byte without modification". Tablespaces outside the data directory must be included and their symlinks archived as links. `pg_wal/` contents, `postmaster.pid`, `postmaster.opts` and `pg_internal.init` should be omitted, and omitting `pg_replslot/` is advised. — [PostgreSQL docs: Continuous Archiving](https://www.postgresql.org/docs/current/continuous-archiving.html)
- Native incremental backup (`pg_basebackup --incremental`, PG17+) needs the earlier backup's `backup_manifest` and WAL summaries in `pg_wal/summaries`. "If the required summary files are not present, an attempt to take an incremental backup will fail." The summaries must cover every LSN from the prior backup's start LSN to the current one. PostgreSQL itself does not track which backups depend on which. — [PostgreSQL docs: Continuous Archiving](https://www.postgresql.org/docs/current/continuous-archiving.html)

**ZFS**
- `zfs send -i` sends a single increment. "The incremental source must be an earlier snapshot in the destination's history." `-I` "sends all intermediary snapshots" between the two snapshots. — [OpenZFS zfs-send(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html)
- An incremental source can be a bookmark (`-i snapshot|bookmark`), so the sender does not have to keep the old snapshot. — [OpenZFS zfs-send(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html)
- Resumable transfers: `zfs send -t <token>` "creates a send stream which resumes an interrupted receive". The token is the `receive_resume_token` property on the receiving dataset, which `zfs receive -s` sets up. — [OpenZFS zfs-send(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html)
- `-w` (raw) sends encrypted data "exactly as it exists on disk", and a non-raw send of encrypted data disables later raw incrementals. `-c` keeps on-disk compression in the stream. `-L` allows blocks larger than 128 KiB. Without `-L`, large blocks are split on receive, which can prevent later reverse incrementals. — [OpenZFS zfs-send(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html)
- Practitioner pattern (old, around 2013): seed a standby with `zfs send -R | ssh zfs recv -F` from a snapshot of the primary's data directory, then switch to streaming replication. PGCon 2013 had an exercise on "updating the slave server using an incremental ZFS send". — [Six Feet Up blog](https://sixfeetup.com/blog/replication-with-zfs-and-postgresql); [PGCon 2013 session](https://www.pgcon.org/2013/schedule/events/612.en.html) (search-result summary; page not fetched)

**btrfs**
- `btrfs send -p <parent>` produces an incremental stream relative to "previously sent snapshots that are available on both the sending and receiving side". `-c <clone-src>` adds clone sources. "All snapshots involved in one send command must be read-only", and a read-only mount does not count. Clone sources must be "exactly in the same state on both sides." — [btrfs-send(8)](https://btrfs.readthedocs.io/en/latest/btrfs-send.html)

**LVM thin**
- Thin snapshots share data blocks with the origin and the two "diverge as either are written". A thin snapshot must not be given a size, or LVM creates a classic COW snapshot instead. Chunk size is a multiple of 64 KiB, from 64 KiB to 1 GiB. A thin snapshot can also use a read-only "external origin". When the pool runs out of space, writes queue for up to 60 seconds by default and then fail, which can damage the filesystem. — [lvmthin(7)](https://man7.org/linux/man-pages/man7/lvmthin.7.html)

**Thin-clone tooling built on these primitives**
- Postgres.ai DBLab Engine builds thin clones on ZFS or LVM2 copy-on-write from one full physical copy, and refreshes that copy through physical provisioning (pg_basebackup, WAL-G, pgBackRest) or logical dump/restore. It claims a 10 TiB clone in under 2 seconds for one user and about 30 seconds with 15 concurrent users. With ZFS it "routinely takes new snapshots of the data directory". For managed services without physical access it runs on a separate VM and does periodic full refreshes. — [Postgres.ai DBLab docs](https://postgres.ai/docs/database-lab); [DBLab GitHub](https://github.com/postgres-ai/database-lab-engine) (search-result summary; vendor claims)

### Inferences
- Every snapshot-diff mechanism here (ZFS `-i`, btrfs `-p`, and by analogy LVM) uses lineage: the receiver must hold a snapshot that is bit-identical to the sender's base. Once the destination copy is started as a server, promoted, or written to, that common base is gone unless it was kept as a separate snapshot. A forced rollback on receive discards local changes; this behaviour is from general ZFS knowledge and was not re-verified here. The project's content-hash refresh targets exactly the case where no shared lineage exists.
- Snapshot copies made this way carry no `backup_manifest` and no `pg_wal/summaries` for the source's LSN range. A crash-consistent snapshot also has no `backup_label`. To PostgreSQL such a copy is either a crashed instance (simultaneous snapshot) or a low-level-API backup.
- The tablespace/WAL-on-separate-volume caveat matters in practice. Any refresh tool working on snapshot-derived copies should expect `pg_tblspc` symlinks pointing to other mounts and `pg_wal` as a symlink.

### Gaps
- I did not find a current (2024–2026) authoritative guide on rebuilding a diverged PostgreSQL standby with incremental `zfs send`. The available material dates from about 2013.
- No published numbers on typical incremental ZFS or btrfs stream sizes for PostgreSQL workloads. These depend on recordsize versus the 8 KiB page size and on full_page_writes, and no source here quantifies them.
- lvmthin(7) does not mention a tool for listing changed blocks between thin snapshots. `thin_delta` from thin-provisioning-tools exists to my knowledge but was not verified in this pass.

## 2. Cloud block-storage incremental snapshots (AWS EBS, Google PD/Hyperdisk, Azure managed disks) and how managed Postgres services use them

### Takeaway
All three clouds make disk snapshots incremental at the block level: the first is full and later ones store only changed blocks. AWS and Azure expose APIs that list changed blocks between two snapshots of the same lineage, using 512 KiB blocks on EBS. Managed PostgreSQL services build their backups on these snapshots. RDS takes "storage volume snapshots", Azure Database for PostgreSQL Flexible Server uses managed-disk incremental snapshots plus WAL archiving, and Cloud SQL backups are incremental over "the underlying storage snapshot". RDS also seeds read replicas from a snapshot and then switches to engine-native replication.

### Cited Findings
**AWS EBS**
- "The first snapshot that you create from a volume is always a *full snapshot*... Subsequent snapshots of the same volume are *incremental snapshots*." Worked example: a 200 GiB volume holding 50 GiB gives a 50 GiB first snapshot. After 20 GiB is changed and 10 GiB added, the second snapshot is 30 GiB. — [How EBS snapshots work](https://docs.aws.amazon.com/ebs/latest/userguide/how_snapshots_work.html)
- Lineage carries through restores. A snapshot of Vol 2, created from Snap A of Vol 1, "is an incremental snapshot of Snap A, even though it was created from a different volume". It becomes a full snapshot if Snap A was shared from another account or Vol 2 uses a different KMS key. Archiving converts an incremental snapshot into a full one. — [How EBS snapshots work](https://docs.aws.amazon.com/ebs/latest/userguide/how_snapshots_work.html)
- EBS direct APIs have six actions. Reads are `ListSnapshotBlocks`, `ListChangedBlocks` ("blocks that are different between two specified snapshots of the same volume and snapshot lineage") and `GetSnapshotBlock`. Writes are `StartSnapshot`, `PutSnapshotBlock` and `CompleteSnapshot`. Block indexes are in units of 512 KiB (524,288 bytes). Every block carries a SHA256 checksum, and block tokens are temporary. Public snapshots and Outposts local snapshots are not supported. — [EBS direct APIs concepts](https://docs.aws.amazon.com/ebs/latest/userguide/ebsapi-elements.html)
- AWS aims the direct APIs at backup ISVs, to "track incremental changes on your EBS volumes through snapshots... without having to create new volumes from snapshots" and compare them on EC2. They can also write on-premises data straight into EBS snapshots. — [EBS direct APIs overview](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-accessing-snapshot.html)

**Google Persistent Disk / Hyperdisk**
- Standard snapshots are incremental: "each snapshot contains only the data that has changed since the previous snapshot". The first is a full copy. Standard and archive snapshots live in one or more regions apart from the disk and outlive it. Instant snapshots stay in the disk's zone or region, are not redundant, and are deleted with the disk. Globally scoped snapshots (the default) can be restored in any region. — [Compute Engine disk snapshots](https://docs.cloud.google.com/compute/docs/disks/snapshots)

**Azure managed disks**
- Incremental snapshots: "The first incremental snapshot is a full copy of the disk. The subsequent incremental snapshots occupy only delta changes". They are billed on used size only and use Standard HDD storage (ZRS where available). — [Azure incremental snapshots](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-incremental-snapshots) (page dated 2026-08-19)
- Lineage breaks: you "can't get the changes between snapshots taken before and after you changed the size of the parent disk across 4-TB boundary". Changing SKU or size, and "in rare cases, Azure service updates", can start a new `IncrementalSnapshotFamilyId`. Changes can't be read across families, and the first snapshot in a new family is full. Limits are seven incremental snapshots per disk per five minutes and 500 per disk. — [Azure incremental snapshots](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-incremental-snapshots)
- Azure lets you "get the changes between two incremental snapshots of the same managed disk, down to the block level". — [Azure: copy incremental snapshot across regions](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-copy-incremental-snapshot-across-regions) (page dated 2026-09-16)

**How managed PostgreSQL services use these snapshots**
- Amazon RDS: automated backups are "a storage volume snapshot of your DB instance, backing up the entire DB instance". "The first snapshot of a DB instance contains the data for the full database. Subsequent snapshots... are incremental". Backups are stored in S3. Snapshots and PITR cover multi-volume configurations. — [RDS backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html)
- RDS read replicas: "Amazon RDS takes a snapshot of the source instance and creates a read-only instance from the snapshot. Amazon RDS then uses the asynchronous replication method for the DB engine". — [RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html)
- Azure Database for PostgreSQL Flexible Server: "Data volumes... are backed up through managed disk incremental snapshots from the primary server", plus WAL archiving to Blob storage. Snapshots are daily and are skipped if nothing changed. The snapshot "takes only a few seconds". RPO is up to five minutes. PITR restores the snapshot and then replays WAL. "Fast restore" restores the snapshot alone with no log replay. Backup files can't be exported. The doc contradicts itself: one place says "consecutive snapshots are differential backups" and the FAQ says "Subsequent snapshot backups are incremental." — [Azure PG Flexible Server backup and restore](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore) (dated 2026-07-05)
- Cloud SQL for PostgreSQL: "All Cloud SQL backups, except the first one, are incremental". "Backups encompass the entire disk of the instance". A troubleshooting note mentions "the underlying storage snapshot". Replicas do not have backups. — [Cloud SQL backups](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups)
- Cloud SQL replicas use asynchronous WAL streaming. A cross-region replica is created the same way as an in-region one. — [Cloud SQL replication](https://docs.cloud.google.com/sql/docs/postgres/replication) (search-result summary; page not fetched)
- Supabase seeds read replicas "using a physical backup as a starting point" and catches up from WAL archives (WAL-G to S3) plus streaming from the primary. Restore time scales with database size. — [Supabase read replicas](https://supabase.com/docs/guides/platform/read-replicas); [Supabase blog: introducing read replicas](https://supabase.com/blog/introducing-read-replicas) (search-result summary; page not fetched)

### Inferences
- Snapshot-based managed services (RDS, Azure Flexible Server, Cloud SQL) create copies as "volume snapshot + WAL replay" inside the provider. Customers can't read or refresh those physical files themselves: Azure says backups "can't [be] export[ed]", and RDS and Cloud SQL give no filesystem access. A file-level delta refresh tool is therefore most relevant to self-managed Postgres on VMs, bare metal, or Kubernetes, including AlloyDB Omni.
- `ListChangedBlocks` and Azure's snapshot diff are a lineage-based delta, the cloud equivalent of `zfs send -i`. They are cheap when the destination is an untouched restore of an earlier snapshot in the same family. They give nothing when the destination came from another source, such as a pg_basebackup, a different account or key, a resize across Azure's 4 TB boundary, or a new snapshot family.
- A self-managed Postgres on EBS, PD, or Azure disks that is backed up by disk snapshots produces exactly the "older copy without pg_basebackup metadata" case. Restoring an old snapshot to a new volume gives a crash-consistent PGDATA with no `backup_manifest`, no summaries for the gap, and possibly no `backup_label`.

### Gaps
- Cloud SQL's docs, as fetched, do not say how a new read replica is seeded (disk snapshot/clone or a pg_basebackup-style copy).
- I did not get Google PD/Hyperdisk snapshot rate limits or a public changed-block API comparable to EBS direct APIs. To my knowledge GCP has no public changed-block-list API for PD snapshots, but this was not verified.
- The GCP snapshot doc did not state crash-consistent versus application-consistent semantics in the fetched portion. It only links guides for Linux application-consistent snapshots and Windows VSS.

## 3. Disaggregated-storage Postgres (Aurora, Neon/Lakebase, AlloyDB, AlloyDB Omni, HorizonDB): how replicas and clones are made, and whether they ever reuse an older copy

### Takeaway
In log-is-the-database systems (Aurora, AlloyDB, Neon/Lakebase, HorizonDB), only WAL goes from compute to storage, and the storage tier materializes pages. Read replicas share one storage copy, and clones or branches are copy-on-write metadata operations, so in-region "copying" is close to free and no older copy is ever reused. Cross-region copies are made by service-internal, storage-level replication (Aurora Global Database, AlloyDB secondary clusters) or are not offered yet (HorizonDB preview). AlloyDB Omni, the self-managed edition, is different. It uses ordinary local storage: HA standbys are full second copies, backups go through pgBackRest (documented for container deployments) or an operator backupPlan, and clones are PITR restores. That puts Omni squarely in the "older physical copy" world.

### Cited Findings
**Amazon Aurora (PostgreSQL and MySQL)**
- Aurora cloning "uses a *copy-on-write protocol*". "When the clone is created, no data is copied. Rather, the clone points to the same set of pages as the source". Storage is allocated only as source or clone diverges. — [Aurora cloning](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Clone.html)
- Limits: "up to 15 clones with copy-on-write protocol. After you have 15 clones, the next clone that you create is a full copy", and the full-copy protocol "acts like a point-in-time recovery". "You can't create a clone in a different AWS Region." Cross-VPC is allowed when subnets map to the same AZs, and cross-account is allowed via AWS RAM. Cloning is invoked as `restore-db-cluster-to-point-in-time --restore-type copy-on-write`. — [Aurora cloning](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Clone.html)
- Billing example: the parent has 1000 pages and the clone modifies 100. The parent is billed for 1000 and the clone for 100. If the source is deleted, the clone is billed for all 1000. — [Aurora cloning](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Clone.html)
- Aurora Global Database: one primary Region and up to 10 read-only secondary Regions. Replication uses "dedicated infrastructure, with latency typically under a second", and "Aurora uses the cluster storage volume and not the database engine for fast, low-overhead replication". — [Aurora Global Database](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html)
- Design basis (2017, older): Verbitski et al., SIGMOD 2017. Logging and storage move off the engine, and "by only writing redo log records to storage, we are able to reduce network IOPS by an order of magnitude". The paper describes the MySQL-compatible engine. Aurora PostgreSQL uses the same storage service, but these sources do not detail it. — [Aurora SIGMOD'17 paper (MIT mirror)](https://pdos.csail.mit.edu/6.824/papers/aurora.pdf); [All Things Distributed summary](https://www.allthingsdistributed.com/2017/05/amazon-aurora-design-considerations.html) (search-result summary; paper not fetched in full)

**Neon and Databricks Lakebase**
- Compute is unmodified Postgres with no durable state. WAL goes to a quorum of safekeepers (Paxos), and "a transaction is considered committed once a quorum of safekeepers has acknowledged the WAL record". The pageserver materializes page versions from base pages plus WAL at a requested LSN. Object storage holds long-term immutable history. — [Neon architecture overview](https://neon.com/docs/introduction/architecture-overview)
- Branching: "The new branch points to an existing point in history and begins diverging from there using copy-on-write semantics", and "only new or modified data consumes additional storage". Branches, restores, replicas and new compute attachment are all described as metadata operations. The page gives no numeric benchmarks. — [Neon architecture overview](https://neon.com/docs/introduction/architecture-overview)
- "In 2025, Neon joined Databricks." Neon and Databricks Lakebase run "the same infrastructure, the same technology, and the same core feature set". Branches are "copy-on-write views over shared storage". Lakebase is GA on AWS and in beta on Azure and GCP. Neon runs on AWS only, and its Azure support is being deprecated. — [Neon and Lakebase](https://neon.com/docs/introduction/neon-and-lakebase)
- Secondary sources say the acquisition was announced in May 2025 and Lakebase reached GA in February 2026. One practitioner measured a 1.09 s data-plane branch of a ~63 MB database. — [Thoughtworks: Backstage on Lakebase](https://www.thoughtworks.com/en-us/insights/blog/data-engineering/backstage-lakebase-databricks); [refontelearning summary](https://www.refontelearning.com/blog/databricks-neon-acquisition-lakebase-serverless-postgres) (search-result summaries; not verified against Databricks primary sources)

**Google AlloyDB (managed)**
- Storage (May 2022 blog, older) has three parts: "a low-latency, regional log storage service", a "log processing service (LPS) that processes these WAL records and produces 'materialized' database blocks", and "sharded, regional block storage". "There is no need to checkpoint the database layer, or any reason to send complete database blocks to the storage layer". Reads specify an LSN. Shards can be reassigned between LPS nodes with no data copying. — [Google Cloud blog: AlloyDB intelligent storage](https://cloud.google.com/blog/products/databases/alloydb-for-postgresql-intelligent-scalable-storage/)
- Read replicas: "each replica instance doesn't require its own storage". "Creation of a read replica instance is very fast as data can be incrementally loaded from the storage layer on demand", with WAL streamed to replicas to invalidate cached pages. Storage spans three zones, each holding "a complete copy". "Backup operations are completely handled by the storage service". — [Google Cloud blog: AlloyDB intelligent storage](https://cloud.google.com/blog/products/databases/alloydb-for-postgresql-intelligent-scalable-storage/)
- Cross-region: up to five secondary clusters per primary, replicating asynchronously. The "replication stream updates the storage volume in the secondary region". Switchover gives 0 RPO, and cross-region failover is in Preview. The doc does not say how a secondary is first populated or what it costs. — [AlloyDB cross-region replication](https://docs.cloud.google.com/alloydb/docs/cross-region-replication/about-cross-region-replication)

**AlloyDB Omni (self-managed: containers and Kubernetes operator)**
- Containers: "If you run AlloyDB Omni in a container on individual servers, we recommend you use pgBackRest". pgBackRest ships in the container and supports building "clone clusters, either to a current or to a specific point in time". "Any solution that lets you back up from and restore to a PostgreSQL cluster running in a Docker or Podman container also works". The page does not mention disk snapshots. — [AlloyDB Omni backup overview (16.3.0)](https://docs.cloud.google.com/alloydb/omni/containers/16.3.0/docs/backup-overview)
- pgBackRest setup and restore pages exist for versions 15.5.x through 18.x. Restore needs the same AlloyDB Omni major version. TDE clusters support pgBackRest. There is also a pgBackRest page under the Kubernetes 15.7.0 tree. — [Set up pgBackRest (18.1.0)](https://docs.cloud.google.com/alloydb/omni/containers/18.1.0/docs/set-up-pgbackrest); [Restore with pgBackRest (18.3.0)](https://docs.cloud.google.com/alloydb/omni/containers/18.3.0/docs/restore-pgbackrest); [Kubernetes 15.7.0 pgBackRest page](https://docs.cloud.google.com/alloydb/omni/kubernetes/15.7.0/docs/set-up-pgbackrest) (search-result summaries)
- Kubernetes operator: backups come from a `backupPlan` resource with cron schedules for `full`, `differential` and `incremental`. Storage can be local, a Cloud Storage bucket, or S3-compatible. Retention is 1–90 days (default 14). Backups can be taken from the primary or a standby. A `Restore` "overwrites all of your database cluster's data". Clone-from-PITR works only "within the same namespace and same kubernetes cluster". The page does not name the backup tool. — [AlloyDB Omni: Back up and restore in Kubernetes (16.11.0)](https://docs.cloud.google.com/alloydb/omni/kubernetes/16.11.0/docs/backup-kubernetes)
- Operator HA: `numberOfStandbys` (maximum 5). Prerequisites are "storage for two complete copies of your data". Failover promotes a standby, deletes the old primary, and creates a new standby. The operator supports cross-region DR standbys in remote clusters. — [AlloyDB Omni Kubernetes HA (18.1.0)](https://docs.cloud.google.com/alloydb/omni/kubernetes/18.1.0/docs/kubernetes-ha); [AlloyDB Omni Kubernetes overview](https://docs.cloud.google.com/alloydb/omni/kubernetes/18.1.0/docs/overview) (search-result summaries)

**Azure HorizonDB (preview)**
- "Disaggregated compute and storage architecture with a database-as-a-log design". There are two storage fleets, one for WAL and one for data. "Data pages aren't written from the compute replicas to the storage layer. WAL is the authoritative source of truth". Read replicas share "a single copy of the data in zone resilient storage", so they provision quickly with "no data replication". Backups "are implemented as snapshots of the blobs". walsender, the archiver, checkpointing, and pg_basebackup/pg_backup_start-style backups are all offloaded to storage. — [What is Azure HorizonDB?](https://learn.microsoft.com/en-us/azure/horizondb/overview) (updated 2026-09-22)
- As of that page, HorizonDB is still in preview. "Cross region read replicas... isn't yet supported", backup retention is fixed at seven days, and there is no CMK. — [What is Azure HorizonDB?](https://learn.microsoft.com/en-us/azure/horizondb/overview)
- Announced at Ignite in November 2025. Microsoft claims 3,072 vCores across primary and replicas and up to 128 TB of storage. — [InfoQ](https://infoq.com/news/2025/12/azure-horizondb-postgresql/); [The New Stack](https://thenewstack.io/microsofts-azure-horizondb-takes-on-aurora-alloydb/) (search-result summaries; vendor claims)

### Inferences
- Disaggregated managed services never need to "reuse an older copy". Their replicas share storage, and clones and branches are COW pointers into versioned storage. Cross-region secondaries are kept current by storage-level log shipping. A service-internal "refresh" amounts to pointing at a newer LSN or creating a new COW clone, not moving data. The likely exception is how a cross-region secondary (Aurora Global, AlloyDB secondary) is first populated, which the docs do not describe.
- Self-managed AlloyDB Omni behaves like vanilla PostgreSQL. Standbys are full copies, rebuilt after failover ("a new standby replica is created"). Backups are pgBackRest or an operator backupPlan with full/diff/incr schedules, and clones are PITR restores. A delta-refresh tool would fit Omni when re-seeding a standby or DR copy from an older, diverged physical copy rather than doing a full re-copy. That is especially true across Kubernetes clusters, since operator clones are limited to the same namespace and cluster.
- pgBackRest and operator restores leave tool-specific manifests (pgBackRest's own `backup.manifest`), not PostgreSQL's `backup_manifest`, unless pg_basebackup was used. A restored-and-started copy is just a PGDATA. The pgBackRest behaviour is from general knowledge and was not verified in this pass.

### Gaps
- Whether the AlloyDB Omni Kubernetes operator uses pgBackRest internally for `backupPlan`, and how it seeds a new standby (pg_basebackup, pgBackRest restore, or a volume snapshot). The fetched pages do not say.
- How Aurora Global Database and AlloyDB secondary clusters are first seeded across regions (full storage copy versus snapshot restore), and the egress cost of that seeding. Not documented in the pages fetched.
- Microsoft Socrates (SIGMOD 2019) and the Aurora SIGMOD 2018 paper were not fetched, so no claims are made from them here.
- Neon/Lakebase branch-creation and restore times: Neon's docs give no numbers ("restarted instantly", "fast and predictable").

## 4. Cross-region and bandwidth-constrained refresh

### Takeaway
Clouds keep repeated cross-region copies cheap only when the destination still holds the previous copy in the same lineage. EBS cross-region snapshot copies and Azure managed copies are incremental after the first. GCP Async Replication sends all used blocks once and then only changed blocks. When that lineage is missing (first copy, new KMS key, a new region, a rebuilt replica), the services send everything again. RDS cross-region read-replica creation always ships a full snapshot copy.

### Cited Findings
- EBS: "If you copy a snapshot to a new Region, a full (non-incremental) copy is created". Encrypting to a new KMS key also makes a full copy. Later cross-Region or cross-account copies are incremental only if the snapshot "was copied to the destination Region or account previously", the most recent copy still exists and has not been archived, and all copies use the same KMS key. Cross-Region transfer incurs EC2 data-transfer charges. There is a limit of 20 concurrent copies per destination, and an optional "time-based copy" sets a completion duration in 15-minute increments. — [Copy an EBS snapshot](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-copy-snapshot.html)
- RDS cross-Region read replica: RDS takes an automated snapshot, does a "cross-Region snapshot copy for the initial data transfer", loads the replica from it, deletes the copy, and then replicates changes made since the operation started. "This process can take hours". Data transfer charges apply both to the snapshot transfer and to ongoing replication. For RDS PostgreSQL, deleting the source sets a cross-Region replica's status to `terminated`; the replica is not promoted. — [RDS cross-Region read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.XRgn.html)
- Azure managed copy (`CopyStart`): "Azure copies only the changes since the last snapshot in the target region", and you are "only billed for the bandwidth cost of the cross-region data transfer and the read transactions on the source snapshot". Snapshots must be copied in creation order, one per disk at a time, with up to 100 parallel per subscription per region. "Only incremental snapshots can be copied across regions". The manual alternative reads block-level changes between two incremental snapshots and applies them to a base blob in the target region, using your own compute for speed. — [Azure: copy incremental snapshot across regions](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-copy-incremental-snapshot-across-regions)
- GCP PD/Hyperdisk Asynchronous Replication: first "replicates all the used blocks on the primary disk to the secondary disk", then only changed blocks, and blocks changed several times are sent once. The "target RPO of one minute, for up to 12.5 GB of compressed changed blocks per minute" is not configurable. It works between regions on the same continent. Consistency groups align replication across multiple disks to "a common point in time". Supported disks are Balanced/SSD PD and Hyperdisk Balanced, Balanced HA and Extreme. Failover is the customer's job. — [GCP Async Replication](https://docs.cloud.google.com/compute/docs/disks/async-pd/about); [launch blog (2023, older)](https://cloud.google.com/blog/products/compute/introducing-persistent-disk-asynchronous-replication)
- Azure PG Flexible Server geo-redundant backups replicate to the paired region asynchronously with "up to one hour of delay". PITR is not available in the remote region, only "the last available backup data". — [Azure PG Flexible Server backup and restore](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore)
- Aurora Global Database: storage-level replication with latency "typically under a second". Aurora clones cannot cross Regions. — [Aurora Global Database](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html); [Aurora cloning](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Clone.html)
- Within a Region, RDS charges nothing for replica data transfer. For MySQL/MariaDB, AWS suggests chaining cross-Region replicas to pay for one transfer. — [RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html); [RDS cross-Region read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.XRgn.html)

### Inferences
- The clouds' delta mechanisms assume an unbroken chain of snapshots on both sides. Recreating a cross-region RDS replica after a break, for example after promotion or a terminated replica, re-ships a full snapshot even though the destination region may still hold a nearly identical old copy. This is the gap a content-addressed chunk-diff refresh fills for self-managed clusters.
- For bandwidth-limited links, the documented tools are: (a) keep a chain of snapshots in the destination (EBS, Azure), (b) run continuous block replication (GCP Async), or (c) use storage-level log shipping (Aurora Global, AlloyDB secondaries). None of these can turn an arbitrary diverged PGDATA back into a current copy.

### Gaps
- Cross-region egress prices per GB (EC2 inter-region, GCP inter-region, Azure inter-region) were not retrieved from the pricing pages in this pass.
- GCP Async Replication pricing and network charges were cut off in the fetched page.
- How Google charges, and in what increments, for restoring global snapshots into another region was not retrieved.

## 5. Published numbers: snapshot and clone speed, incremental sizes, costs

### Takeaway
Hard numbers mostly come from docs examples and limits, not benchmarks. EBS reads and writes in 512 KiB blocks at fractions of a cent per thousand. Snapshots are sized by changed data. GCP Async Replication targets a one-minute RPO up to 12.5 GB of compressed changes per minute. Vendor claims for COW clones are "seconds regardless of size". Independent benchmarks of clone or snapshot speed for PostgreSQL were not found.

### Cited Findings
- EBS direct APIs pricing (example Region): `ListChangedBlocks`/`ListSnapshotBlocks` cost $0.0006 per 1,000 requests, `GetSnapshotBlock` $0.003 per 1,000 blocks returned, and `PutSnapshotBlock` $0.006 per 1,000 blocks written. Same-Region transfer between the APIs and EC2 is free on non-FIPS endpoints, and PrivateLink/NAT/TGW processing fees apply if those are in the path. — [EBS direct APIs pricing](https://docs.aws.amazon.com/ebs/latest/userguide/ebsapi-pricing.html)
- EBS snapshot sizing examples: 50 GiB full, then a 30 GiB incremental after 20 GiB changed and 10 GiB added. Three snapshots totalling 16 GiB in the 10/4/2 GiB example. — [How EBS snapshots work](https://docs.aws.amazon.com/ebs/latest/userguide/how_snapshots_work.html)
- Azure: snapshots are billed on used size (a 10 GiB snapshot appears as 10 GiB/31 days per day on the usage report). An empty incremental snapshot is 0 MiB, or 6 MiB for 4096-byte-sector disks. Limits are 7 snapshots per disk per 5 minutes and 500 per disk. — [Azure incremental snapshots](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-incremental-snapshots)
- GCP Async Replication: RPO target 1 minute for up to 12.5 GB of compressed changed blocks per minute, and up to 1,000 disk pairs per region pair per project. — [GCP Async Replication](https://docs.cloud.google.com/compute/docs/disks/async-pd/about)
- Azure PG Flexible Server: snapshot "takes only a few seconds". Restore time from a snapshot "doesn't depend on the size of data", but WAL replay time varies. Free backup storage equals 100% of provisioned storage. — [Azure PG Flexible Server backup and restore](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore)
- Aurora: up to 15 COW clones per source before clones become full copies. Global Database replication latency is "typically under a second". — [Aurora cloning](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Managing.Clone.html); [Aurora Global Database](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database.html)
- DBLab (vendor claim): 10 TiB thin clone in under 2 s for one user, about 30 s with 15 concurrent users. — [Postgres.ai DBLab docs](https://postgres.ai/docs/database-lab) (search-result summary)
- Lakebase (practitioner, anecdotal): a ~63 MB branch in 1.09 s. — [Thoughtworks](https://www.thoughtworks.com/en-us/insights/blog/data-engineering/backstage-lakebase-databricks) (search-result summary)
- Aurora paper (2017): writing only redo to storage cuts network IOPS "by an order of magnitude". — [Aurora SIGMOD'17](https://pdos.csail.mit.edu/6.824/papers/aurora.pdf) (search-result summary)

### Inferences
- My arithmetic from AWS's example prices: reading 1 TiB of changed blocks through `GetSnapshotBlock` means 2^40 / 2^19 = 2,097,152 blocks, about $6.29 in API fees, with no transfer charge to EC2 in the same Region. Because EBS tracks changes at 512 KiB granularity, a single changed 8 KiB PostgreSQL page costs a 512 KiB block transfer. That is up to 64x amplification for scattered writes, versus a page- or chunk-level diff.
- Azure's "billed for bandwidth + source read transactions" for managed cross-region copies means the delta's size, not the disk's size, drives the cost of repeated refreshes. This holds only while the snapshot chain is unbroken.

### Gaps
- No independent measurements of real incremental snapshot sizes for PostgreSQL OLTP workloads, for example how full_page_writes, VACUUM, or hint-bit writes inflate block-level deltas. This would be worth measuring in the project.
- Current per-GB snapshot storage prices (EBS standard/archive, GCP standard/archive/instant, Azure incremental) were not pulled from the pricing pages.
- No published Aurora clone-creation times for large volumes, and no figures for AlloyDB read-pool or clone creation time.

## 6. Which approaches produce copies lacking pg_basebackup metadata ("any older copy" scenarios), and what this implies

### Takeaway
Most physical PostgreSQL copies in the wild are not pg_basebackup outputs. They are restored volume or disk snapshots (crash-consistent, sometimes wrapped in `pg_backup_start/stop`), restores from pgBackRest/WAL-G/Barman, former primaries or standbys after failover, filesystem thin clones (ZFS/LVM/DBLab), or provider-internal snapshot+WAL restores that customers never see as files. None of these leave a PostgreSQL `backup_manifest` or guarantee WAL summaries covering the gap to the current source. PG17+ native incremental backup therefore can't refresh them, and a content-based chunk diff can.

### Cited Findings
- PG17+ incremental backup needs the prior backup's `backup_manifest` and WAL summaries covering the LSN gap, and "if the necessary files have already been removed... the incremental backup will fail". — [PostgreSQL docs: Continuous Archiving](https://www.postgresql.org/docs/current/continuous-archiving.html)
- A volume or filesystem snapshot looks to PostgreSQL like a crashed server and needs WAL replay. Separate WAL or tablespace volumes require simultaneous snapshots. — [PostgreSQL docs: File System Level Backup](https://www.postgresql.org/docs/current/backup-file.html)
- Managed services build copies from volume snapshots plus WAL: RDS ("storage volume snapshot"; read replicas "from the snapshot"), Azure Flexible Server ("managed disk incremental snapshots"), and Cloud SQL ("underlying storage snapshot"). — [RDS backups](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html); [RDS read replicas](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ReadRepl.html); [Azure PG backup](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore); [Cloud SQL backups](https://docs.cloud.google.com/sql/docs/postgres/backup-recovery/backups)
- Supabase seeds replicas from a physical backup plus WAL-G archives. — [Supabase read replicas](https://supabase.com/docs/guides/platform/read-replicas) (search-result summary)
- AlloyDB Omni recommends pgBackRest for container deployments and uses an operator backupPlan (full/diff/incr) on Kubernetes. HA standbys are full copies, recreated after failover. — [AlloyDB Omni backup overview](https://docs.cloud.google.com/alloydb/omni/containers/16.3.0/docs/backup-overview); [AlloyDB Omni K8s backup](https://docs.cloud.google.com/alloydb/omni/kubernetes/16.11.0/docs/backup-kubernetes); [AlloyDB Omni K8s HA](https://docs.cloud.google.com/alloydb/omni/kubernetes/18.1.0/docs/kubernetes-ha)
- DBLab keeps one physical copy (from pg_basebackup, WAL-G, pgBackRest, or a dump) plus periodic ZFS snapshots for thin clones. — [Postgres.ai DBLab docs](https://postgres.ai/docs/database-lab) (search-result summary)
- HorizonDB backups are "snapshots of the blobs", and pg_basebackup/pg_backup_start-style backups are offloaded to storage. — [What is Azure HorizonDB?](https://learn.microsoft.com/en-us/azure/horizondb/overview)

### Inferences
Likely sources of an "older physical copy" a refresh tool would meet, roughly ordered by how much metadata they carry:
- Restored cloud disk snapshot or ZFS/LVM/btrfs snapshot of a self-managed server (EC2/GCE/Azure VM, on-prem, or Kubernetes PV snapshots via CSI). No `backup_manifest`, no WAL summaries for the gap, and usually no `backup_label` unless a low-level-API wrapper was used. If it was ever started, it has diverged with its own timeline or WAL.
- Former primary or standby after failover or promotion, including AlloyDB Omni and Patroni-style clusters. This is a full PGDATA on a diverged timeline: pg_rewind territory, which other researchers cover.
- pgBackRest, WAL-G, or Barman restores, including AlloyDB Omni's recommended path and Supabase's replica seeding. These carry tool-specific manifests that a PostgreSQL-native incremental cannot use.
- Thin clones and branches (DBLab on ZFS/LVM, Aurora clones, Neon/Lakebase branches). The first is a self-managed PGDATA. The others are not reachable as files.
- Provider-internal snapshot+WAL restores (RDS, Cloud SQL, Azure Flexible Server PITR). No customer file access, so they are out of scope for a file-level refresh tool.

What the project should take from this:
- Lineage-based deltas (ZFS/btrfs send, EBS `ListChangedBlocks`, Azure snapshot diff, GCP Async) only work while both sides share an untouched common ancestor. A content-hash refresh, comparing per-chunk digests on both sides, is the general fallback that works for any older copy. It is also finer-grained than EBS's 512 KiB blocks.
- Correctness after a content-based refresh still needs a consistent source image: a simultaneous snapshot, or a `pg_backup_start/stop`-bracketed copy with `backup_label`/`tablespace_map`, followed by WAL replay. Comparing data alone is not enough. The tool also has to deal with multi-volume layouts (separate `pg_wal`, tablespaces).
- Fully disaggregated managed services (Aurora, AlloyDB managed, Neon/Lakebase, HorizonDB) do not need this kind of tool internally. Its natural home is self-managed and hybrid deployments, AlloyDB Omni in particular, plus cross-region or cross-cluster DR where cloud snapshot lineage has broken.

### Gaps
- I found no survey or dataset quantifying how real-world Postgres copies are made (share made by snapshots versus pg_basebackup versus pgBackRest/WAL-G). The sponsor's claim that "most real-world copies are not made with pg_basebackup" fits the evidence that managed services and common tools use snapshots or third-party backup tools, but no source measures it.
- Kubernetes CSI VolumeSnapshot practice for Postgres operators (CloudNativePG volume-snapshot backups, Crunchy PGO) was not covered in this pass and is another likely source of snapshot-derived copies.
